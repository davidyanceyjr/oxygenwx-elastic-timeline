## Scope and invariants

- Build debug-local names, authored event-period model and metadata. Materialize supported typed events over the established deterministic synthetic baseline. The authored period is an event-editing range, not a shorter catalog window.
- Preserve the existing canonical catalog, codec, `CatalogWindow`, namespaces, schema and coordinator-owned activation/selection path. Every SIMULATED and REPLAY recording retains the complete D-30..D+13 local-date horizon and location IANA timezone identity.
- Preserve timezone/DST rules and typed support. Missing values remain unavailable, probability remains distinct from amount, unsupported conditions remain absent, and no weather semantics are invented. Preserve established SIMULATED support outside the authored event period.
- Save/reopen editable SIMULATED recordings with fixture-distinct identities and consistent metadata. Capture REPLAY only explicitly, preserving the saved SIMULATED values and origin under a distinct REPLAY identity; a later SIMULATED edit cannot change the snapshot.
- Saving is not activation. Only an explicit preview of a saved SIMULATED or REPLAY record may activate synthetic data. The preview request identifies the selected location, storage namespace/origin, and dataset ID, then uses the coordinator's existing request sequencing, cancellation/supersession checks, staging, and guarded selection publication. For saved preview, keep the requested target as pending request data, separate from the published selection: while B loads and validates, the currently published active selection and selected location (for example, A) remain intact. Loading status may change, but do not clear or relabel the published selection before commit. The coordinator loads and validates the saved record at the activation boundary and stages the returned recording; REPLAY uses the existing REPLAY-origin projection while retaining the captured origin in its saved recording. The caller does not load the payload before requesting preview.
- A current saved-preview failure must leave the full previously published active selection intact, including its location, recording identity, selected instant, and view generation, even when the requested preview targets another location. Keep the coordinator's published selected location consistent with that preserved selection. A valid saved result is published only through the coordinator's current-request commit path: after confirming the request is still current, atomically publish the target location and its staged active selection in the process-local debug view. This commit does not change the durable saved-location choice or location records. Preserve the existing successful-selection timestamp rules for the target; retaining A during staging must not make A's selected instant an implicit target-selection anchor. A stale or superseded request must neither publish nor roll back over a newer request's state. Missing, invalid, or inconsistent saved records fail without activation, source lookup/load, a storage-write attempt, or false success. This saved-only preview path is separate from ordinary SIMULATED/REPLAY activation, whose existing source-generation fallback remains available.
- Replacing the active selection with a valid preview does not delete or overwrite A's durable catalog or saved-location data. This slice does not change the saved-location catalog update lifecycle or its user-selected refresh interval; scheduled catalog updates remain out of scope.
- Do not mutate LIVE/provider/cache/location state, import LIVE solar summaries, alter shared schema or storage compatibility, or create a second activation/selection owner. If safe preview cannot use the authorized additive coordinator/debug seam, stop and replan within the original DFM.4 boundary.

## Risks and stop conditions

- Existing debug code from cycle 084 is unaccepted and may conflict with the split plan; review before editing and preserve unrelated work.
- Repository evidence: `CatalogActivationCoordinator.loadIsolated` returns the stored SIMULATED/REPLAY recording when valid. On Missing/Invalid it falls through to the registered source, validates its generated recording, and attempts persistence under the requested identity. This is source-generation fallback; the current code does not establish a separate value-substitution operation. In the ordinary coordinator path, a request for another location also clears the published active selection before loading, and a failure preserves it only when its location matches the request. The saved-only path is new execution work: keep B in pending request state, retain A in published selection state, and make the coordinator's existing sequence/request authority sufficient to guard the B commit without using the published location as the target. Bypass source generation and persistence on saved-record failure; preserve the complete prior active selection across location changes; and atomically publish B only after successful validation and a current-request check. Retaining A while staging must not change the established successful-selection timestamp choice for B. Keep A's durable catalog and saved-location data intact, and leave its scheduled update lifecycle unchanged. Keep ordinary activation fallback and selection semantics intact. If this cannot be done without changing shared schema, LIVE behavior, or coordinator selection ownership, stop and replan within the original DFM.4 boundary.
