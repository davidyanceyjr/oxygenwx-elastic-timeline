## Functional invariants and state contract

- On first launch with no saved selection, show a clear manual “Choose location” action and no local forecast values. Selecting a search result persists it and begins a location-scoped load; it does not turn sample data into local weather.
- For a committed switch to a different location, the coordinator publishes the new selected location, `active = null`, loading, and cleared prior error in one `CatalogActivationState` update. Retain the preceding selected `Instant` as a pending selection anchor for the new catalog's existing preserve-or-clamp rule; carry that anchor through further location choices or retries made before a catalog activates, and clear it only after a validated catalog activates. Do not publish a transient state pairing the new location with the previous catalog. A matching target cache may activate even when its refresh failed; in that case show the cache's actual delivery/freshness and the typed refresh failure. If neither a matching cache nor a usable source result exists, keep `active = null` and show no forecast values.
- For a request or refresh of the same location, keep its valid active catalog available while loading. On a failed LIVE refresh with a matching active catalog, retain that exact active selection and its delivery/freshness metadata, even if the repository also returns an older cached fallback; publish the failed refresh outcome separately. This avoids relabeling currently displayed source data as cache or replacing it with an older snapshot because a later refresh failed. If there is no active matching catalog, a matching cached fallback may activate with its actual cache/staleness metadata while the failed refresh remains visible. On success, replace the catalog atomically and preserve or clamp selected time. Keep view generations monotonic across location switches and replacements so callbacks from a former view cannot select time in a later view even when the old `active` selection was cleared.
- Keep `selectedLocation` and `active.location` equal whenever `active` is non-null. Treat this as a coordinator publication invariant, with a defensive UI gate before projecting forecast values. Presentation receives typed selected-place and request/refresh outcome values; it formats user-facing status without provider DTOs or a second mutable source of truth.
- Resolve the coordinator state transition at its existing boundary. `CatalogActivationCoordinator` owns request sequencing, the pending selected-time anchor, and a monotonic generation counter independent of nullable `state.active`; `MainActivity` only renders a catalog when its location matches the published selection. Increment the counter on each current validated activation, including after a switch that cleared `active`; do not derive it from `previous?.viewGeneration`. `selectInstant()` continues to require the current active generation, so a callback from A cannot select time in a later B view.
- Apply one publication rule to each transition: a different-location commitment publishes `(selected = B, active = null, loading = true, error = null)` in one `StateFlow` write before starting B's request; a same-location request/refresh publishes loading while retaining only its matching active catalog; a current validated result publishes its matching catalog and advances generation; a current failure retains the matching active catalog, otherwise activates only a matching usable cache or leaves `active = null`. Superseded results and failures publish nothing. Save the last active selected `Instant` as a pending anchor on the first switch and carry it through further choices until a validated catalog activates; then use the existing preserve-or-clamp rule. Selector dismissal without a committed choice changes neither selected time nor scale.
- Keep repository outcome semantics distinct at the coordinator/presenter boundary. `CatalogRepositoryResult` already carries `delivery`, `freshness`, `refresh`, and `storedAt`; propagate the typed `CatalogRefreshStatus` rather than converting an empty result into a generic activation error or discarding its refresh outcome. `SKIPPED` means no fetch was attempted, `SUCCESS`/`PARTIAL` describe usable source results, and `NO_DATA`/`INVALID_REQUEST`/`TRANSPORT_FAILURE` describe failed fetches even if a matching cache is displayed. When a same-location failed LIVE refresh has an active catalog, retain that active catalog; when no active catalog exists, the repository's matching stale fallback remains eligible for activation. Expose status independently from the catalog's actual delivery/freshness. A no-cache result exposes the typed failure and no forecast values. Presenter-formatted labels may explain these statuses, but must not infer source success from the mere presence of a catalog or treat `storedAt` as the forecast issue time.
- On relaunch with a saved selection, restore that place and request only its compatible LIVE dataset. A matching cache may populate immediately; show its freshness and retrieval context. Follow the existing whole-catalog refresh policy; explicit refresh is foreground-only.
- Show the saved place name with LIVE/cache delivery, freshness, last successful retrieval where known, and any current refresh failure. `LiveCatalogRepository.load()` already returns `CatalogRepositoryResult.refresh`, including failure when it falls back to a matching cache; propagate that typed outcome through activation and presentation instead of discarding it. A no-cache result must expose its failure reason without forecast values. Keep missing forecast facts unavailable. Do not collapse source, cache delivery, staleness, coverage, or request failure into one ambiguous label.
- The header location control opens the existing manual selector. Selecting another place switches the target selection. Until its own valid cache or source result is available, show target-location loading/empty/error state; never show the previous place's facts under the target name. A failed target fetch without cache shows no forecast values and offers retry/recovery.
- Same-location refresh keeps its last valid matching catalog usable; on refresh failure, show that active catalog's actual delivery and freshness context and expose the failed request. A matching cache returned by the repository can activate when no matching catalog was already active; label that fallback cached/stale. Do not replace or relabel an already active source result solely because a later request failed. A successful load atomically replaces it and preserves selected `Instant` when possible, otherwise the established clamping rule applies.
- Preserve the immersive timeline, 44-local-date catalog semantics, exact selected-time authority, accessible forecast browser, source/provenance truth, responsiveness, predictable gesture ownership, and readability. Opening/dismissing the selector must return to the same timeline selection and scale.
- `SampleForecast` remains a development fallback only and stays visibly labeled as synthetic wherever its existing debug path is used. No normal production state may attribute it to a saved/search location.
