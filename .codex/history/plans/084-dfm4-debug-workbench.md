## Debug-session restoration contract

- **Ownership and compatibility:** `CatalogActivationCoordinator` is the sole owner of checkpoint capture and restoration. Add a coordinator-produced opaque, process-local checkpoint value; the debug delegate may retain and return it but may not construct, edit, or restore individual coordinator fields. Keep the coordinator's existing request sequencing and state publication as the single activation owner. Existing startup, activation, selection, and refresh callers retain their current behavior; the new API is additive and does not add a second presentation/preview selection path.
- **Startup readiness:** expose a coordinator-owned awaitable readiness signal for the complete saved-location startup operation. It is pending while the saved-location read is outstanding and, if that read selects a location, until the initial catalog activation reaches terminal success or failure. Empty, invalid, and failed saved-location restoration are terminal startup outcomes too; readiness resolves without inventing an active catalog or retrying. Do not derive this signal from `CatalogActivationState.loading`: `restoreStartup()` performs the saved-location read before `beginRequest()` sets `loading`, and the initial activation is launched separately. Keep readiness out of ordinary UI state so normal startup presentation remains unchanged.
- **Alternate cold-launch readiness:** `CatalogPickerDelegate.onMainActivityCreated` can consume a debug catalog intent, so `MainActivity` does not call `restoreStartupCatalog()` on that path. Register that alternate startup synchronously with the coordinator before launching asynchronous intent handling; readiness remains pending during intent validation, saved-location lookup, activation, and any required fixture selected-time operation. Complete it only after the handler and the resulting current activation reach a terminal success or failure, including a superseding activation. If the existing cold-launch error path invokes `restoreStartupCatalog()`, transfer readiness to that restoration and its initial activation; do not signal ready between the failure and fallback. Preserve the existing debug request, picker, SG.4 replay fixture, and failure behavior without introducing an extra saved-location restoration or LIVE refresh on a successful debug launch. A pending `#DEBUG` is consumed and waits for the resulting settled state just as on ordinary startup; no command is forwarded to geocoding. Use an explicit lifecycle-scoped handshake between the debug delegate and coordinator, with the coordinator retaining ownership of readiness and activation sequencing. A canceled/destroyed host must not publish a false settled state; a newly created coordinator establishes readiness for its own startup path.
- **Request completion and fixture selection:** provide a narrow coordinator-produced completion handle for debug activation using the existing request sequence. Every issued handle reaches success, failure, or superseded when that request reaches the corresponding outcome; a failed or replaced request must not leave a caller waiting for a dataset that will never activate. Keep sequencing and completion publication inside the coordinator and its existing synchronization boundary. Do not expose mutable request controls or require ordinary callers to adopt the handle. Replace the SG.4 delegate's dataset-matching `state.first` wait with this completion result. On success, use the successful selection's existing `viewGeneration` with `selectInstant`; its existing stale-generation guard prevents a fixture selection from affecting a replacement catalog. On failure, preserve the existing request-error, picker, and cold-launch restoration fallback. On supersession, skip fixture selection and do not start fallback restoration or replace the newer request; preserve picker behavior, finish the handler's startup participation, and let coordinator readiness wait for the current activation. This completion handle reports activation only: startup readiness still includes handler work and any required fixture selection.
- **Cancellation:** catch and rethrow `CancellationException` before ordinary debug-request error handling. Host destruction/cancellation must not open a picker, initiate fallback restoration, or mark startup ready. Do not complete alternate startup unconditionally in `finally`; complete or transfer its participation only on the defined non-canceled paths. Keep readiness and handles process-local and lifecycle-scoped; add no persistence, polling, arbitrary delay, general event bus, or parallel state owner.
- **Debug entry:** the shared location controller offers the submitted query to the generic variant hook before geocoding. The debug delegate consumes exact `#DEBUG`; it consumes exact `#PICKER` only while the debug session is active. In normal or pending-entry state, `#PICKER` is unconsumed ordinary search text, as the approved behavior board specifies. If `#DEBUG` arrives before startup readiness, retain it as a pending entry action and wait for the coordinator signal; do not pass it to search/geocoding, cancel or replace startup work, or request a preview. Before capture, the coordinator also confirms any later activation request is terminal; if one is in flight, defer entry until it succeeds or fails rather than canceling/replacing it. Once the coordinator is settled, capture the checkpoint before opening the debug session. `#PICKER` remains unavailable until that session is active. A settled empty or error state is checkpointable and must not trigger a retry or be represented as an active LIVE catalog.
- **Atomic settled capture:** waiting for readiness or an activation to finish is not itself permission to capture: a newer activation can start before capture. Recheck startup readiness and the current activation's terminal status under the coordinator's existing synchronization boundary, and capture under that same boundary only when both hold. If either condition changed, wait for the current operation and retry the check; do not cancel it or hold the synchronization boundary while suspending. Keep this coordination additive to the existing request sequencer and ordinary callers.
- **Checkpoint contents:** under the coordinator's existing synchronization boundary, capture the selected location, selected-location name, last activation request, active selection and interval, pending selection anchor, and complete published `CatalogActivationState`. Capture only a settled state. The checkpoint preserves the existing active catalog object and exact `selectedInstant`; restoration does not recompute selection from wall time, `asOf`, or a new catalog window. Keep request sequence/job control inside the coordinator rather than exposing or rewinding those controls through the checkpoint.
- **Session exit and stale work:** before publishing restored state, the coordinator cancels any in-flight preview request and advances/invalidates its existing request sequence so a late completion cannot publish over the restored state. Perform invalidation and checkpoint restoration within the coordinator's existing synchronization boundary as one state transition. Restore coordinator-owned fields and published activation state directly from the checkpoint; do not call `restoreStartup`, `requestCatalog`, `refreshCurrent`, a provider, a catalog source, or storage to reconstruct it. The restoration path performs no catalog load, provider request, or storage write.
- **Exit before ordinary actions:** use the same coordinator restoration operation as explicit Exit. The debug delegate invalidates pending debug entry and session-owned preview/fixture continuations, restores any active checkpoint, clears session/overlay state, and discards the checkpoint before returning from the generic before-action callback. With no active session, the callback only cancels any pending debug-entry action; it does not cancel startup or restore a nonexistent checkpoint. Run the existing `store.select` or `refreshCurrent` path only after the callback returns successfully. For selection, restoration must precede the persistent selection write, not just the post-write coordinator notification. For refresh/retry, restore first so `lastRequest` belongs to the restored catalog rather than the preview. If the ordinary action subsequently fails, retain its existing failure handling and remain outside debug; do not restore the discarded checkpoint again. Release/no-delegate behavior is a no-op callback followed by the original action. Keep this ordering in the existing delegate/controller/activity seams; add no action queue, generic session framework, second activation owner, or checkpoint rebasing.
- **Forbidden changes:** do not change ordinary activation behavior, catalog/source semantics, storage namespaces, database schema, `CatalogWindow`, `RecordedCatalogCodec`, or the selected-time presentation route. Do not add a parallel preview selection path, persist the checkpoint, expose coordinator internals to the UI, or put developer-command names/parsing in main-source search code.
- **Focused proof:** add/run only the already-authorized DFM.4 focused tests. Cover readiness remaining pending while saved-location restore is delayed even when `state.loading` is false; readiness resolving after initial activation success/failure and for empty/invalid/error startup outcomes; alternate cold-launch readiness remaining pending through intent handling, activation, and required fixture selection; successful and failed alternate launches including fallback restoration and a superseding activation; a pending consumed `#DEBUG` entering only after the settled result without invoking search or adding a LIVE refresh; a new activation starting between an initial readiness observation and capture, with entry waiting for and capturing its settled result; exact active and settled-empty/error checkpoint round trips; no provider/storage calls during restoration; and a canceled/superseded preview completion being unable to overwrite the restored state. Preserve the existing release command-isolation checks.
- **Ordinary-action proof:** within the scoped DFM.4 tests, cover location selection and refresh during an active session, including an in-flight preview. Assert checkpoint restoration precedes the selection write or refresh request, restoration itself makes no provider/storage calls, the normal action follows its existing path without duplicate dispatch, and stale session work cannot reopen debug or overwrite the result. Check selection-write failure and refresh failure retain existing handling with debug/overlay off; a later exit is harmless; pending debug entry is canceled by the ordinary action; and no-session/release behavior remains unchanged.
- **Completion/cancellation proof:** within those focused tests, cover success, failure, and supersession of the debug request handle; failed/superseded SG.4 activation terminating its wait; fixture selection occurring only for its successful generation; supersession causing no fallback and readiness remaining pending until the replacement activation settles; failure transferring readiness through the existing cold-launch fallback without an intermediate ready state; and host cancellation causing no picker, fallback, or false readiness. Include cancellation/supersession caused by checkpoint restoration so no completion waiter is stranded. Do not broaden verification beyond DFM.4.
