## Resolved execution contracts

### Debug activation request and startup precedence

- The picker sends one explicit, versioned debug request containing the saved `LocationId`, `CatalogOrigin`, dataset ID, and (for REPLAY only) replay recording ID. LIVE carries the force-refresh choice. The debug-only variant delegate does not trust a serialized `CatalogLocation`: it resolves the ID through the host's `SavedLocationRepository.find` and accepts the request only when that saved row decodes successfully. Reject unknown action/version, malformed enum or IDs, missing locations, and origin/ID combinations that violate `CatalogActivationRequest` invariants; never fall back to another location or origin.
- `MainActivity` remains the sole owner of one `CatalogActivationCoordinator`. Keep it available to both the initial-intent path and `onNewIntent`; the debug activity must not construct a coordinator, source registry, repository, or active-catalog state of its own. Handle a cold-launch request after constructing the coordinator. Route from the picker with `FLAG_ACTIVITY_CLEAR_TOP | FLAG_ACTIVITY_SINGLE_TOP` so an existing MainActivity receives `onNewIntent` and absence of one creates it cold; call `setIntent` and pass the new intent through the same request handler exactly once.
- Normal startup restoration runs only when there is no debug activation request to handle. A validated explicit request updates the coordinator's in-memory request location and enters its existing sequenced `beginRequest` path without calling `SavedLocationRepository.select` or changing the persisted selected-location pointer. If startup restoration had already begun before a new intent arrives, the explicit request must advance the coordinator sequence so the late restore result and any older load cannot publish over it. Add only the location-explicit activation entry point needed for this behavior; retain the coordinator's existing cancellation, request validation, whole-catalog publication, and failure-preserves-active-state rules.
- A rejected intent or missing/malformed saved-location row must not start a catalog load. Preserve the previous active catalog when the activity already has one; on cold launch, allow ordinary startup restoration to proceed after rejection. Report request validation and coordinator loading/active/error state through the debug flow as a read-only projection of the MainActivity-owned coordinator state; a debug-only callback/event relay may carry that state, but must not become a second catalog owner or activation path. Include a retry/correction path. The timeline continues to render `SampleForecast` and must not present coordinator activation as changed forecast values.

### Deterministic Chicago replay-fixture preparation

- Use the saved Chicago `CatalogLocation` resolved from the current saved-location list. Request `SimulatedCatalogSource` with dataset ID `wx22-chicago-replay-v1` and `asOf = 2026-10-28T12:00:00Z`; require a usable result whose location, ID, `asOf`, and captured provenance (`SIMULATED`) match that request, then wrap that canonical source result in the existing `CatalogRecording` representation.
- First call `CatalogDatasetStorage.load(location, REPLAY, datasetId)`. A `Found` recording is retained unchanged only after its decoded location, dataset ID, fixed `asOf`, and captured `SIMULATED` provenance are confirmed. Treat `Missing`, `Invalid`, or a `Found` recording that fails any fixed-fixture identity check as needing deterministic regeneration and replacement using `CatalogDatasetStorage.save(REPLAY, recording)`; `save` replaces prior rows for that location/namespace/dataset ID. Do not edit provenance, facts, support, or codec payload. Propagate preparation/save failures as an explicit picker error and do not offer a replay row as ready.
- After generation or replacement, call `load` again and require `Found` with the expected identities and SIMULATED provenance. Then confirm the dataset ID appears in `history`; history establishes discoverability only and is not a substitute for successful payload validation. Repeated preparation leaves a valid matching fixture intact and repairs a missing or invalid one from the same fixed inputs.
- The stored recording retains SIMULATED captured provenance in the REPLAY namespace. Activation goes through the coordinator's existing REPLAY branch, which validates the stored recording and exposes REPLAY as active provenance. Do not activate directly from the simulated source or treat the stored row itself as active REPLAY data.

No database migration, provider contract change, request construction change, catalog schema change, renderer/projection migration, or change to `SampleForecast` is in scope. The transport execution-context correction above is the only additional production scope. If the existing coordinator cannot be routed without duplicating activation ownership or changing startup/selector policy, stop and record the concrete mismatch for review before expanding this boundary.

## Functional invariants

- A request identifies exactly one saved `CatalogLocation`, origin, and dataset ID; REPLAY also carries the explicit replay recording ID, equal to the dataset ID.
- LIVE, SIMULATED, and REPLAY use the existing coordinator and isolated storage namespaces. Do not merge facts, provenance, cache metadata, or locations. A failed/rejected request leaves the last valid catalog active and gives the user a clear recovery path.
- Before the picker offers REPLAY, debug-only fixture preparation creates or validates one deterministic Chicago recording by loading the canonical simulated dataset for Chicago using the fixed dataset ID and `asOf` instant above, then persisting the resulting original `CatalogRecording` in the REPLAY namespace. Check it with `CatalogDatasetStorage.load`, since `history` alone lists identities without validating payloads. Keep stored provenance SIMULATED; the existing replay activation path supplies active REPLAY provenance. Do not generate a second catalog schema, alter the recording payload, or treat the fixture as LIVE data. Repeated preparation must be safe and must leave a valid existing fixture intact.
- The debug location choice is temporary activation context. It does not rewrite the persisted selected-location pointer. Empty or malformed saved-location/replay lists show an explicit state; they do not silently pick another location or source.
- The active catalog's origin and delivery/freshness labels are truthful. The displayed immersive scene remains the existing DEMO `SampleForecast` until WX.23; the debug UI must not imply the canonical catalog is already rendered there.
- Existing three `DebugForecastProfiles`, scenario entry, timeline gestures, and legacy profile invocation remain usable. Do not convert the legacy 7/11/14-day fixtures into a 44-day catalog or change the timeline's forecast values.
- No process restart is required to activate another origin. The UI can leave and reopen the debug activity while the app process remains alive.
- Release manifests, DEX, and source sets contain no debug picker activity, profile catalog, replay fixture, debug delegate provider, request contract, or request handler. The generic variant callback interface may remain in main, with no release provider/resource registration.
