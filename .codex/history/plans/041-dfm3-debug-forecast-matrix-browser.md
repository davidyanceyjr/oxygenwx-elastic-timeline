## Resolved integration and time semantics

- Owner decision on 2026-10-26: use a neutral presentation-source contract in main presentation types. It carries the selected sample's neutral condition label, exact common forecast facts, provenance, and optional thunderstorm/warning facts without referring to debug catalog types. Debug profile definitions and profile resolution remain in `src/debug`; only the scenic `SkyFrame` adapter maps debug-only condition vocabulary to the renderer's supported visual inputs. The debug condition and all typed source facts remain intact in the debug profile.

- Add a presentation-layer forecast-source contract in `app/src/main` that supplies ordered valid times, exact loaded bounds, daily dates/summary inputs, and the selected-time presentation needed by `TimeLabScreen` and `ElasticForecastTimeline`. Adapt `SampleForecast` to this contract and keep it as the normal default. The UI and timeline consume the supplied source rather than reading `SampleForecast` directly.
- Implement the profile source and catalog adapter in `app/src/debug`. The shared screen receives the source through injection; main/release code must not import, name, or resolve debug catalog types. Resolve the profile ID in a debug-only activity/tooling entry point and pass the resulting source into the shared full-screen scene and tape. Use an explicit debug launch path; add no persistent scenario control to the immersive screen. If the variant manifest/source-set boundary cannot provide this path without a main-to-debug reference, stop and revise the plan before implementing the browser path.
- The selected forecast valid time for a debug profile is always one of that profile's exact hourly sample timestamps. Hourly scrubbing snaps to an available hourly sample; it never creates a fractional reported valid time. The selected timestamp and displayed hourly facts come from that exact catalog sample. Any continuous scene transition between samples is decorative, remains separate from text/accessibility forecast facts, and is not labeled as a forecast report.
- A daily tap selects the profile's exact local-noon sample for that date. The daily overview uses that sample for condition and other point facts; its low/high may be calculated only as the minimum/maximum temperatures among that date's explicit hourly samples. Keep the overview clearly identified as a daily representation.
- Each profile declares an exact `referenceTime` that is one of its loaded hourly samples. Initial debug selection and the debug meaning of “return to now” both resolve to this reference sample; do not compare synthetic profile dates with the device wall clock. The normal `SampleForecast` source retains its existing wall-clock-to-fixture behavior. Day navigation, scrubbing, accessibility actions, and all bounds use the injected source's actual loaded horizon.
- The source contract belongs to this isolated prototype's presentation boundary. It must not change `SampleForecast`, canonical production forecast models, production oxygenWX, or introduce provider/network behavior. Preserve all DFM.2 debug records and extended debug-only facts in their own typed catalog; do not coerce unsupported debug facts into canonical types merely to satisfy the shared screen.

Do not interpolate reported facts or carry missing fields forward. Keep any intra-hour visual continuity decorative and do not label it as a reported forecast value.

The source contract and source-driven bounds/day counts are the planned seam for variable horizons; the debug profile supplies the exact loaded samples and bounds. If that seam cannot be kept within this prototype's presentation/UI boundary and release isolation, stop and revise the plan before expanding scope.
- Debug profile dates are synthetic. Each profile must explicitly identify its `referenceTime` sample for initial selection and “return to now”; using device wall-clock arithmetic against those dates is prohibited. Normal fixture reset behavior remains unchanged.
- The concept uses illustrative display values to communicate scrubbing. Implementation values must be defined in the debug scenarios and must not be copied blindly from the generated artwork.
- Preserve every existing DFM.2 row and transition sequence unchanged. If representing full forecast profiles requires changing those approved row/sequence contracts or canonical production types, stop and revise the plan rather than silently expanding those interfaces.
- Focused unit tests are authorized only for DFM.3 profile construction, complete horizons/buffers, exact-sample projection, and daily noon/extrema semantics. Application-wide and instrumentation tests remain out of scope.
