## Scope

- Add Open-Meteo daily `sunrise` and `sunset` to the existing daily request, which already sends the catalog coordinates, IANA timezone, and `timeformat=unixtime`.
- Map returned sunrise/sunset epoch seconds to nullable `Instant` values on the matching provider nominal daily date. Derive the daily row label from `daily.time` plus the response's fixed `utc_offset_seconds`, as documented; convert the solar event instants through the requested IANA zone to validate their local dates and complete local-day support. Keep absent, null, or unavailable events absent.
- Extend `ProviderDailySummary` and its daily field/support reporting for sunrise and sunset. Preserve their values through captured/recorded catalogs with a new recording schema version while continuing to read existing recording versions as unavailable for fields they do not contain.
- Carry the selected local date's solar events through the catalog projection into `SceneReading`, alongside the unchanged selected `Instant`. The shared result must be available to clear, cloudy, rain, and storm scene treatments; weather overlays cannot shift the solar event times.
- Use provider events as the only sunrise/sunset boundary for the sun cue. At sunrise and sunset the cue meets the horizon; outside the event interval no visible sun is drawn. Do not snap, clamp, or retarget timeline selection to a solar event. For catalogs without solar data, do not invent a sun event or retain a time-only cue that implies one.
- Keep the existing theme-owned night cue separate from the provider-timed sun cue. Preserve its current decorative behavior without treating it as a lunar phase or solar event.
- Preserve the owner-directed cloud behavior as a renderer-only projection of the existing scene state and selected forecast time. Ordinary rain uses one coherent bank entering from one edge; heavy-rain/storm states use two coherent banks entering from opposite edges and converging. Do not encode cloud motion as wind, cloud speed, or a measured event time. The existing cloud-transition board remains visual reference for the motion checkpoints; the approved combined board governs the solar/data flow and city/cloud depth.
- Interleave the city depth explicitly: sky/light, distant blue buildings, cloud banks, then middle/foreground buildings and canopy. Clouds may occlude the distant blue buildings; the middle-ground must occlude the clouds. If the current flattened architecture artwork cannot express this ordering, split it into pixel-aligned distant and middle/foreground layers without changing the composition or bounds. Preserve matching source-canvas dimensions, transparency, and the existing viewport crop/alignment so the split reconstructs the current composition without shifting or seams.
- Derive the cloud pose from `SceneReading.selectedInstant` in the location's IANA zone and the existing typed weather state. Replace interval-relative repeating drift with a deterministic, smooth local-time path through the storyboard's 06:00, 12:00, and 18:00 reference poses. Interpolate between adjacent poses and hold outside the path boundaries; do not loop, reverse, use per-frame randomness, or advance from wall-clock time. When reduced motion is active, keep one still pose with the same weather meaning. Keep the pose calculation local to the first-city renderer; add no provider fields, canonical model types, animation framework, or timeline behavior.
- Keep the current selected-time forecast text, gesture ownership, and timeline behavior unchanged.
- Review the official Forecast API field catalog and record a discovery-only map of currently requested/mapped fields and candidates that could support a future details page. Do not add those candidates to this cycle's API request, canonical catalog, or UI.
