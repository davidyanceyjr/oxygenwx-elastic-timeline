## Invariants and mapping decisions

- Retain the WX.12 fixed request: `past_days=30`, `forecast_days=14`, metric units, coordinates, `timeformat=unixtime`, 15 hourly and seven daily variables. Check the response zone against the requested IANA zone. Interpret Unix seconds as `Instant`; assign dates using that zone, never a fixed UTC offset.
- **Timestamp contract, checked against the captured response and provider documentation on 2026-10-28:** Hourly Unix seconds are UTC instants; convert to `Instant` and assign local date/time with the requested IANA zone. Daily Unix seconds are also epoch seconds, but their *nominal provider date* is recovered using the response's fixed `utc_offset_seconds` (equivalent to `Instant` plus that fixed offset, then `LocalDate`), not `Instant.atZone(requestedZone).toLocalDate()`. The Chicago capture has `utc_offset_seconds=-18000`; its final daily timestamp is `2026-11-10T05:00Z`, which is nominal date 2026-11-10 under the fixed offset but 2026-11-09 under post-transition IANA rules. Keep these two operations distinct: use the validated nominal date as daily identity, and requested-IANA-zone `[date.atStartOfDay, nextDate.atStartOfDay)` as its support. Do not infer support boundaries from the provider's fixed offset. Validate daily timestamps as strictly increasing one-day nominal dates inside the 44-date target; reject duplicates, gaps only as coverage missingness, and out-of-window dates. Provider docs: [Forecast API timestamp documentation](https://open-meteo.com/en/docs), reviewed 2026-10-28. This confirms the intended parser rule; the fixture matrix below still must prove fall and spring transition behavior. **Before mapper implementation, compare that contract with distinct fall-back and spring-forward fixtures. If either boundary fixture contradicts hourly or daily identity/support semantics, stop before mapping, preserve the fixture and observed values as evidence, and revise/review this plan's contract and dependent coverage design before implementation. Do not silently adapt the parser or dismiss the fixture as malformed.**
- Map matching hourly temperature, humidity, precipitation probability, cloud cover, wind, pressure, and visibility into nullable canonical fields. Convert visibility m to km and snow depth m to cm; snowfall is cm. Represent hourly precipitation, rain, and snowfall as preceding-hour `[t−1h,t)` accumulations. Do not turn amounts into instantaneous rates. Preserve missing values separately from zero.
- Map documented WMO codes to condition/phenomenon sets. An unknown but well-formed code leaves the code-derived condition/phenomenon unavailable and makes their declared coverage incomplete while retaining independent valid measurements; malformed code values invalidate the response. Codes never supply thunderstorm probability, hail/tornado probability, severity, or official alerts. Keep rain, total precipitation, and snowfall independent.
- Add a provider-neutral, typed daily summary keyed by validated provider nominal date to the canonical snapshot. It holds nullable supplied temperature maximum/minimum, precipitation-probability maximum, mapped weather-code condition/phenomena, and rain/total-precipitation/snowfall amounts with true IANA local-day support. Mark these values `PROVIDER_SUPPLIED`; hourly-derived summaries remain separate and explicitly `DERIVED`. An omitted or null daily value stays unavailable, and a daily row is never inferred from hourly samples. Add daily expected/received coverage so a missing supported daily field or date contributes to `Partial` independently of hourly coverage; do not treat a nullable daily summary as complete merely because the row exists.
- Construct D−30 through D+13, exactly 44 local date identities at request `asOf`. Require the response date range to align with that captured `asOf`; a response anchored to another local day is an invalid response, not a relabeled dataset. Allow 23/25-hour DST dates, missing hours, null variables, short horizons, and partial days. **Coverage oracle:** derive expected support from the fixed request, requested/documented supported variables, the captured `asOf`, and the complete IANA-zone grid across all 44 local dates—not from returned arrays. Each valid instant in a date contributes one expected point for each requested supported point field. For each requested accumulated field, construct the one-hour intervals wholly within each true local date; map each expected `[t−1h,t)` interval to the provider value whose valid time is its end `t`. This keeps midnight-ending intervals assigned to the preceding date and makes 23/25-hour dates yield 23/25 expected intervals. Derive expected daily support independently as one supported value per requested daily field per target date. A missing returned row/value or a null at expected support is missing coverage; an unsupported/unrequested variable is excluded. Keep support generation separate from decoding/normalizing provider rows. Do not invent facts or zeroes. Reject malformed lengths/times/units, conflicting duplicates, and out-of-range values; sort harmless out-of-order samples deterministically. A response with no usable hourly facts is `NoData`, never a `Success` with empty facts under WX.9.
- **Owner decision, 2026-10-28: date-level product segments.** Add provider-neutral product segments to the same canonical catalog, with inclusive start and exclusive end local dates, product kind, and only verified source/model identity and issue time. Segments are disjoint, ordered, and confined to the 44-date window. For each date D−30…D+13, assign a product kind iff at least one hourly or daily row is returned for that nominal/local date; row presence counts even if every value in it is null. Dates before D are `ARCHIVED_MODEL_FORECAST`; D and later dates are `FORECAST`. Coalesce only adjacent dates with the same assigned product kind and verified identity into half-open segments; a missing date breaks a segment. A date with no returned row has no segment, while expected support still declares its missing coverage. The location and `asOf` define all 44 dates, including unassigned dates. Never label archived model values as observations; `asOf` is not issue time. Do not invent a model-run ID or issue timestamp: the auto-model response may stitch multiple runs. The captured Chicago response has hourly and daily rows on all 44 dates, so this rule yields two adjacent segments split at D; sparse fixtures must prove gaps and null-only rows behave as stated.
- Keep one canonical catalog and one WX.9 source result regardless of location or product segment. The existing catalog-level provenance remains the delivery/source envelope; add an explicit aggregate `MIXED` product kind for catalogs with more than one segment kind. Date-level segments are authoritative for the meaning of each covered date; `MIXED` is not a meteorological product or observation claim. A one-kind catalog retains that kind at the envelope level. Existing single-product synthetic catalogs retain their current semantics. For Open-Meteo, the source ID identifies the provider/Forecast API; leave model/product ID and issue time null unless the response explicitly verifies them.
- Extend the WX.11 recording codec to **schema v2** for date-level segments, typed daily summaries, and daily support. Decode existing v1 recordings unchanged with their original uniform-product meaning; do not invent absent segments or daily values in decoded v1. V2 encodes/decodes all segments, daily nulls, units, support, and original source metadata losslessly; replay changes delivery origin only and retains product meanings. Keep existing v1 writer output byte-compatible for v1-shaped recordings or provide an explicit v1 writer path for the existing approved fixture. Reject unsupported versions and malformed segment/daily shapes explicitly; document deterministic ordering and both versions' replay behavior.
- Preserve current synthetic fixtures, debug scenarios, timeline selection, gestures, atmosphere, DEMO DATA labeling, and accessibility. Keep the source dormant and cancellation propagating.
